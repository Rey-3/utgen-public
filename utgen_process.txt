UTGEN FULL PROCESS
==================

This describes the current implementation in the workspace.

The real entry point is generate_from_config.py. The design document mentions
cli.py and pipeline.py, but those files are not present in the current code.


1. OVERALL CALL ORDER
---------------------

generate_from_config.py
  __main__
    mp.freeze_support()
    run()
      projects_from_config()
      ModuleIndexer.index()
        IncludeScanner
        configure_libclang()
        ClangParser.parse()
        function_definitions()
        for every function:
          InventoryBuilder.build()
          AtomBuilder
          DecisionExtractor.extract()
          BodyIrBuilder.build()
          DataflowEngine.analyze()
      XmlDbWriter.write()
      for every FunctionIR:
        run_function()
          child process: generate_function()
            RowAssembler.assemble()
              McdcGenerator
              Solver
              CoverageGenerator
              optional BoundaryGenerator
              optional FaultGenerator
            Verifier.check()
              Interpreter.run()
            ValueXmlWriter.write()
            StubXmlWriter.write()
            ReportWriter.write()


There is also a database-only path in regenerate_pdm_ut.py:

regenerate()
  optional ModuleIndexer.index()       only with --rebuild
  XmlDbReader.read()
  RowAssembler.assemble()
  Verifier.check()
  ValueXmlWriter.write()
  StubXmlWriter.write()
  ReportWriter.write()


2. PHASE 1: SOURCE INDEXING
---------------------------

2.1 Read configuration

projects_from_config() reads config.yaml.

Input example:

  projects:
  - name: PDM_UT
    root_path: D:\\SW\\liauto_pdc\\Application
    modules:
    - module_name: PDM_MOS_1
      source_file: D:\\SW\\...\\PDM_MOS_1.c
      excel_input_dir: D:\\TestTeamAssets\\common_tools\\v2\\PDM_UT\\PDM_MOS_1

Output:

  projects, include_dirs

The batch creates a ModuleIndexer with compiler defines and include paths.


2.2 Resolve includes

ModuleIndexer.index() creates an IncludeScanner.

IncludeScanner responsibilities:

  - Find every #include.
  - Search recursively under the project root.
  - Handle case-insensitive filenames.
  - Build unique clang -I directories.
  - Record resolved headers and missing headers.

Main methods:

  IncludeScanner.__init__()
    Starts recursive include scanning.

  get_unique_include_dirs()
    Returns the include directories passed to Clang.

  _walk()
    Recursively visits headers.

  _includes_of()
    Extracts include names from one source file.

  _encoding_of()
    Detects file encoding.

  _find_file()
    Recursively searches for a header.

Example output:

  include_dirs = ["D:\\SW\\include", "C:\\MinGW\\include"]
  headers = [("Rte.h", "D:\\SW\\include\\Rte.h", sha256)]


2.3 Configure and run Clang

configure_libclang() loads libclang.dll once.

ClangParser.parse() creates the Clang translation unit using:

  -x c
  -I<include directory>
  -D<define>
  detailed preprocessing records

function_definitions() returns only functions defined in the target .c file.
Static functions in the .c file are included. Functions defined in headers are
ignored.

ParseError represents fatal Clang diagnostics.


2.4 Collect macros and global types

ModuleIndexer._macros() scans the translation unit for macros.

Object-like numeric macros are folded:

  #define LIMIT 10

becomes:

  MacroDef(name="LIMIT", kind="object", raw="10", value=10)

Function-like macros are recorded as raw text.

_register_globals() registers global enums, structs, unions, and variables in
the type graph before functions are processed.


3. PER-FUNCTION INDEXING
------------------------

For every function, ModuleIndexer._function() calls these in order:

  1. InventoryBuilder.build()
  2. AtomBuilder(...)
  3. DecisionExtractor.extract()
  4. BodyIrBuilder.build()
  5. DataflowEngine.analyze()


3.1 Build the inventory

InventoryBuilder.build() identifies all controllable and observable values:

  - Function parameters
  - Return value
  - Referenced globals
  - Written globals
  - Static locals
  - Pointer addresses
  - Stub return values
  - Stub argument captures

Example:

  uint8 testfunc(uint8 num, mystruct test)

Produces:

  num                 IN
  test.isvalid        IN
  test.code           IN
  testfunc()          OUT

Global directions are determined by usage:

  read only       -> IN
  written only    -> OUT
  read and write  -> INOUT

Important functions:

  build()
    Builds the complete Inventory.

  _scan()
    Scans reads and writes.

  _record_ref()
    Records a parameter or global reference.

  _direction_of()
    Calculates IN, OUT, or INOUT.

  _globals()
    Returns used globals.

  _statics()
    Finds static locals.

  _pointer_address()
    Creates address leaves such as @p.

  _is_assign()
    Detects assignment operators.


3.2 Build the type graph and leaves

TypeGraph stores:

  - Struct definitions
  - Union definitions
  - Enum definitions
  - Member types
  - Array dimensions
  - Bitfield widths
  - Pointer types
  - Function-pointer types

LeafDeriver converts complex types into injectable leaves.

Example:

  typedef struct {
      uint8 isvalid;
      uint8 code;
  } mystruct;

becomes:

  test.isvalid
  test.code

Deep arrays and structures keep their dimensions:

  cfg.abc[4].ded[5]

Function-pointer members are stored in the graph but are not emitted as input
leaves.

Important functions:

  TypeGraph.describe()
    Classifies a Clang type.

  TypeGraph.register()
    Registers a struct, union, or enum.

  _register_record()
    Registers struct or union members.

  _register_enum()
    Registers enum values.

  LeafDeriver.leaves()
    Starts leaf derivation.

  LeafDeriver._emit()
    Recursively explodes members.

  clean_name()
    Removes struct, union, enum, const, and volatile spelling.

  dims_suffix()
    Formats dimensions such as [4][5].


3.3 Find external stubs

StubFinder.find() scans function calls.

Example:

  mystruct lol = get_lol_msg();

Produces:

  Stub:
    get_lol_msg() returns mystruct

  Input leaves:
    tessy_get_lol_msg.isvalid
    tessy_get_lol_msg.code

Same-module helper calls are not stubbed. Void stubs have no injectable return
leaves.

Important functions:

  find()
    Finds all external calls.

  _walk()
    Recursively scans expressions.

  _record()
    Adds one unique stub.

  _is_local_definition()
    Detects same-module helpers.

  _stub_info()
    Builds StubInfo.

  _return_of()
    Resolves the return type.

  _tessy_leaves()
    Creates tessy_* leaves.

Default functions not stubbed:

  memcpy, memset, memcmp, abs


3.4 Convert conditions into atoms

AtomBuilder converts C conditions into a boolean tree.

Example:

  if (x > 10 && flags & 0x02)

becomes conceptually:

  And((
      Atom(x, Op.GT, rhs=10),
      Atom(flags, Op.BITSET, rhs=2),
  ))

Mappings:

  x       -> TRUTHY
  x == 1  -> EQ
  x != 1  -> NE
  x < 1   -> LT
  x <= 1  -> LE
  x > 1   -> GT
  x >= 1  -> GE
  x & 2   -> BITSET

CopyPropagation resolves locals:

  uint8 flag = x > y;
  if (flag)

is mapped back to x > y.

Important functions:

  AtomBuilder.build()
    Builds an atom tree.

  build_case()
    Builds a switch-case equality.

  _node()
    Dispatches condition expressions.

  _relation()
    Builds relational atoms.

  _value()
    Resolves variables and constants.

  _linear()
    Handles expressions such as x + 3.

  _find_variable()
    Maps source paths to inventory leaves.

  _unknown()
    Marks an uncontrollable condition.

  CopyPropagation.record()
    Records declarations and assignments.

  resolve_expr()
    Resolves a local variable to its source expression.

  snapshot(), restore()
    Save and restore branch state.

  merge()
    Merges branch states.


3.5 Extract decisions and guards

DecisionExtractor.extract() assigns decision IDs in source order.

Example:

  if (a > 10) {
      if (b > 5) {
      }
  }

Produces:

  Decision 1: a > 10
  Decision 2: b > 5
  Guard for decision 2: Decision 1 == TRUE

It handles if, else-if, switch, case, default, ternary operators, early
returns, nested conditions, and loop traversal.

Switch default is modeled as:

  not(case1) && not(case2) && not(case3)

Important functions:

  extract()
    Starts decision extraction.

  _statement()
    Dispatches statement types.

  _if()
    Extracts if and else paths.

  _switch()
    Extracts case/default decisions.

  _loop()
    Traverses loop body under a guard.

  _nested_expr()
    Finds ternary decisions.

  _record()
    Creates a Decision.

  _guard()
    Pushes and pops FILO guard state.

  _case_expr()
    Builds case equality expressions.

  _default_expr()
    Builds the default expression.

  _ends_in_return()
    Detects guard clauses.


3.6 Build the body IR

BodyIrBuilder converts the Clang AST into a Clang-free intermediate
representation.

Example:

  uint8 ret = 0;
  if (num > 10) {
      ret = 13;
  }
  return ret;

becomes conceptually:

  Decl("ret", Const(0))
  If(
      decision_id=1,
      condition=Binop(">", Ref("num"), Const(10)),
      then=(Assign(Ref("ret"), Const(13)),),
  )
  Return(Ref("ret"))

Statement IR classes:

  Decl, Assign, If, Switch, SwitchCase, While, For, DoWhile, ExprStmt,
  Return, Break, Unknown

Expression IR classes:

  Ref, Const, Unary, Binop, CallE, Ternary, Cast, Index, MemberE, Phi

Important functions:

  build()
    Builds the complete function IR.

  _statement()
    Converts one statement.

  _declarations()
    Converts local declarations.

  _if(), _switch(), _loop(), _do_loop()
    Build control-flow IR nodes.

  _expr()
    Converts expressions.

  _decision_id()
    Links IR branches to extracted decisions.

  _local_scopes()
    Handles shadowed locals.

  _static_names()
    Names static locals.

  _initializer()
    Finds declaration initializers.

  _literal()
    Converts constants and macros.

  _call_arguments()
    Extracts function-call arguments.


3.7 Run symbolic data-flow

DataflowEngine.analyze() tracks symbolic values through every path.

Example:

  x = get_x_msg().value;
  a = x + 1;
  b = a * 2;
  if (b > 8) {
  }

The condition becomes:

  (tessy_get_x_msg.value + 1) * 2 > 8

It records DataflowPoint, DataflowState, PathConstraint, return states, and
global writes.

Important methods:

  analyze()
    Starts symbolic execution.

  _block(), _statement()
    Process IR blocks and statements.

  _if(), _loop(), _switch()
    Fork and merge control-flow states.

  _branch()
    Adds a path constraint.

  _condition()
    Resolves a condition.

  _assign_lvalue()
    Tracks assignments.

  _pointer_targets(), _member_targets(), _index_targets()
    Resolve pointer/member/array targets.

  _substitute()
    Recursively substitutes symbolic values.

  _call_effect()
    Marks values affected by an external call as unknown.

  _invalidate()
    Invalidates loop-written values.

  _merge()
    Merges states when there are too many paths.

The result is attached to function.dataflow.

  - Functions
  - Parameters

Reader/helper functions include:

  _sha256(), _walk(), _nodes()


5. PHASE 2: GENERATE TEST ROWS
------------------------------

RowAssembler.assemble(function) performs:

  1. Find input leaves.
  2. Create default values.
  3. Process every decision.
  4. Generate MC/DC assignments.
  5. Apply outer guard assignments.
  6. Convert assignments into numeric constraints.
  7. Solve the constraints.
  8. Run concrete coverage search.
  9. Optionally generate boundary rows.
  10. Optionally generate fault rows.
  11. Deduplicate rows.

The normal batch creates RowAssembler with:

  include_boundary=False
  include_fault=False

Direct RowAssembler usage defaults to both enabled.


5.1 MC/DC generation

For:

  if (a && b)

McdcGenerator produces:

  a=true,  b=true
  a=false, b=true
  a=true,  b=false

These are atom assignments, not final numbers.

Main functions:

  eval_expr()
    Evaluates a boolean tree.

  MaskingRecipes.make()
    Creates a canonical true/false assignment.

  McdcGenerator.pairs()
    Finds independence pairs.

  McdcGenerator.rows()
    Deduplicates assignments.

  _context()
    Finds the masking context.

  _fallback_pair()
    Uses a truth-table search for difficult expressions.


5.2 Apply guards and solve

For:

  if (a && b) {
      if (num > 10) {
          ret = 13;
      }
  }

The inner row gets constraints for:

  a == true
  b == true
  num > 10

AtomConstraints.for_outcome() translates conditions to constraints.

Example:

  num > 10       -> Constraint(num, GT, 10)
  not(num > 10)   -> Constraint(num, LE, 10)

Solver.solve() intersects all constraints.

Example input:

  num > 10
  num <= 20
  num != 11

Example output:

  {"num": 12}

Domain handles signed/unsigned values, enums, bit requirements, forbidden
bits, banned values, and empty domains.


5.3 Concrete coverage search

CoverageGenerator uses Interpreter to check whether symbolic rows really reach:

  - Decision true
  - Decision false
  - Each condition true/false
  - MC/DC independence pairs

It is useful for local variables, stub-return members, dynamic indexes,
previous branches, and pointer data flow.


5.4 Boundary rows

BoundaryGenerator handles relational atoms.

For:

  if (x > 10)

It tries:

  x = 9
  x = 10
  x = 11

Values are clamped to the C type range.


5.5 Fault rows

FaultGenerator uses:

  unsigned input -> 0 and maximum
  signed input   -> minimum and maximum
  enum input     -> enum_max + 1
  pointer input  -> NULL

Type overrides are supported, for example:

  FaultGenerator({"uint8": [7]})


6. VERIFY ROWS AND CALCULATE EXPECTED OUTPUTS
---------------------------------------------

Interpreter.run(function, values) executes the body IR.

It records:

  outcomes       decision result
  observed       all observed decision outcomes
  conditions     observed atom patterns
  loops          loop outcomes
  outputs        expected output values
  unknown        outputs that cannot be calculated

Example input:

  {
      "num": 11,
      "test.isvalid": 1,
      "tessy_get_lol_msg.isvalid": 1,
  }

Example output:

  outcomes = {1: True, 2: True}
  outputs = {"testfunc()": 13}

Interpreter supports arithmetic, assignments, C-style division/remainder,
type wraparound, if/else, switch fallthrough, loops, ternaries, pointers,
local helpers, and stub return values.

Verifier.check() runs every row.

If the actual path matches the row intent, it writes row.expected. Otherwise it
adds an intent-mismatch note.


7. EMIT FINAL FILES
-------------------

For each function, the normal batch writes:

  value_<module>_<function>.xml
  stub_<module>_<function>.xml
  report_<module>_<function>.md

The module database is:

  db_<module>.xml


7.1 Value XML

ValueXmlWriter writes one argument per leaf.

Input example:

  <argument name="num"
            len="8"
            format="unsigned"
            direction="in"
            pointer="false"
            range="0,0,0,11"
            testmethod="decision" />

Output leaves do not receive range or testmethod attributes.

Enum numbers are rendered using enum names. Pointer address leaves are merged
into the corresponding pointer input range, and NULL addresses produce NULL.


7.2 Stub XML

StubXmlWriter writes called function names, return types, return variable names,
and argument capture variables.

Example:

  <function name="get_lol_msg">
    <return>
      <type>mystruct</type>
      <name>tessy_get_lol_msg</name>
    </return>
  </function>


7.3 Markdown report

ReportWriter writes:

  - Function name
  - Source file
  - Number of rows
  - Coverage summary
  - One table row per test case
  - Expected outputs
  - Infeasible pairs
  - Uncontrollable conditions
  - Manual actions


8. COMPLETE BASIC EXAMPLE
--------------------------

Input:

  typedef unsigned char uint8;

  typedef struct {
      uint8 isvalid;
      uint8 code;
  } mystruct;

  extern mystruct get_lol_msg(void);

  uint8 testfunc(uint8 num, mystruct test) {
      mystruct lol = get_lol_msg();
      uint8 ret = 0;

      if (lol.isvalid && test.isvalid) {
          if (num > 10) {
              ret = 13;
          }
      }

      return ret;
  }

Indexed leaves:

  num                              IN
  test.isvalid                     IN
  test.code                        IN
  testfunc()                      OUT
  tessy_get_lol_msg.isvalid        IN
  tessy_get_lol_msg.code           IN

Decisions:

  Decision 1:
    tessy_get_lol_msg.isvalid && test.isvalid

  Decision 2:
    num > 10
    Guard: Decision 1 == TRUE

Main batch rows:

  Row 1:
    num=0
    test.isvalid=1
    tessy_get_lol_msg.isvalid=1
    expected testfunc()=0

  Row 2:
    num=0
    test.isvalid=1
    tessy_get_lol_msg.isvalid=0
    expected testfunc()=0

  Row 3:
    num=0
    test.isvalid=0
    tessy_get_lol_msg.isvalid=1
    expected testfunc()=0

  Row 4:
    num=11
    test.isvalid=1
    tessy_get_lol_msg.isvalid=1
    expected testfunc()=13

10. CURRENT IMPLEMENTATION NOTES
---------------------------------

  - generate_from_config.py indexes the C source every run and then generates
    from the in-memory analysis. It does not read the database it just wrote.

  - regenerate_pdm_ut.py is the database-reading path.

  - The normal batch disables boundary and fault generation.

  - There is no current cli.py, pipeline.py, automatic --reindex, or Excel
    generation stage in this repository.

  - The DB stores source/header hashes, but the current reader does not
    automatically validate staleness.

------------------------------------------

This section explains the actual functions and classes in the current utgen

helpers are described together when they only format, parse, or forward data.

Common types used by many functions:

  Path
    A pathlib file path.

  Cursor
    One node in Clang's syntax tree.

  TranslationUnit
    The complete result of parsing one C source file.

  FunctionIR
    The clang-free representation of one function.

  Inventory
    The inputs, outputs, and stubs of one function.

12. generate_from_config.py
---------------------------

Constants:

  CONFIG_PATH
    config.yaml beside the script, or beside the executable when frozen.

  TIME_LOG_PATH
    generation_times.txt beside CONFIG_PATH.

  FUNCTION_TIMEOUT_SECONDS
    Maximum time allowed for one function. Current value: 200 seconds.


projects_from_config()

Input:

  No arguments.

Operation:

  1. Read CONFIG_PATH.
  2. Parse YAML.
  3. Read config["projects"].
  4. Read Tessy.include.
  5. Convert one include string into a one-item tuple.

Return:

  (projects, tessy_include)

Example:

  config:
    Tessy:
      include: C:\MinGW\include
    projects: [...]

  return:
    (projects, ("C:\MinGW\include",))


elapsed(start)

Input:

  start
    A value returned by perf_counter().

Return:

  A string containing elapsed seconds, for example "1.27s".


report_time(message)

Input:

  message
    Text to print and save.

Operation:

  1. Print the message.
  2. Open generation_times.txt in append mode.
  3. Add the message and a newline.

Return:

  None.


fallback_rows(function)

Input:

  function
    A FunctionIR.

Operation:

  Create two rows. Every IN or INOUT leaf is assigned 0 in the first row and
  1 in the second row.

Return:

  Two TestRow objects with:

    kind = "Timeout"
    description = "generation timeout"

This is used when a function exceeds the 200-second timeout.


write_timeout_outputs(function, name, output)

Input:

  function
    The function that timed out.

  name
    Module name.

  output
    Output directory.

Operation:

  1. Call fallback_rows().
  2. Write value XML using the two fallback rows.
  3. Write stub XML.
  4. Write a Markdown report with the timeout note.

Return:

  Number of fallback rows, normally 2.


generate_function(function, name, output, result_queue)

Input:

  function
    One FunctionIR.

  name
    Module name.

  output
    Output directory.

  result_queue
    Multiprocessing queue used to return status to the parent process.

Operation:

  1. Create RowAssembler(Solver(), McdcGenerator()).
  2. Disable boundary generation.
  3. Disable fault generation.
  4. Assemble rows.
  5. Verify rows with Interpreter and Verifier.
  6. Write value XML, stub XML, and report Markdown.
  7. Put ("ok", row_count) into result_queue.

If an exception occurs, put:

  ("error", "ExceptionType: message")

into the queue.

Return:

  None. The result is communicated through result_queue.


run_function(function, name, output, context)

Input:

  function, name, output
    Passed to generate_function().

  context
    Multiprocessing context.

Operation:

  1. Create a multiprocessing queue.
  2. Start a child process running generate_function().
  3. Wait up to FUNCTION_TIMEOUT_SECONDS.
  4. If still alive, terminate it and call write_timeout_outputs().
  5. Otherwise read the result queue.
  6. Raise RuntimeError if the child reported an error.

Return:

  (row_count, timed_out)

Examples:

  (25, False)
  (2, True)


run()

Input:

  No arguments.

Operation:

  1. Call projects_from_config().
  2. Clear generation_times.txt.
  3. Create ModuleIndexer with __GHS__ and configured include paths.
  4. Create a multiprocessing spawn context.
  5. For each project:
       a. For each module:
            i. Create the output directory.
           ii. Call ModuleIndexer.index().
          iii. Call XmlDbWriter.write().
           iv. For each analyzed function, call run_function().
           v. Record timing.
  6. Record module, project, and total timing.

Return:

  None.

This is the first important caller in the normal batch flow.
